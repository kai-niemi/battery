How to run a load test

A load test is defined by the YAML profile Battery was started with. These steps walk through running it from the web UI, from start to findings.

1Check the setup

Confirm the database and isolation level in the banner above. On the Dashboard, the Effective Model shows the parsed configuration, with its before steps, phases, scenarios and after steps listed next to it.

Open Dashboard
2Pick what to run

Select a scenario. Optionally skip the before or after steps, individual phases, or all phases to try the scenario with a single virtual user first. Skipping before steps that capture state can make a scenario fail.

3Start the run

Press Start. The status card turns green, and each phase card shows its progress as virtual users are ramped up. Press Abort to cancel early; running users stop and the run ends as cancelled.

Open Dashboard
4Watch the workers

Each virtual user is a worker with live latency percentiles, throughput and error counts. Filter by status, and open a worker to see its timing, call totals and the exceptions it hit, with stack traces.

Open Workers
5Follow the metrics

Charts show worker latency and throughput over time, and system metrics such as the connection pool. Pending pool threads mean users are queueing for connections, which adds to the measured latency.

Worker Metrics System Metrics
6Review the results

Once all users complete, the Dashboard shows a summary of the run: outcome, throughput, latency, errors, users, pool usage and findings such as pool saturation, dropped users or degrading latency. Recent runs are kept on the Runs page.

Key concepts

Phases control the rate at which virtual users are created. A phase either creates a fixed number of users spread evenly over its duration, or ramps linearly from startRate to maxRate users per second. A phase without either acts as a pause. maxConcurrency caps the active users; users arriving above the cap are dropped, a sign that the database isn't keeping up. Users can outlive their phase, so phases can overlap.

A scenario is the sequence of steps each virtual user repeats for the scenario's duration. A step runs embedded SQL, a Battery Script, or a script file. Before steps run once to prepare, such as creating a schema, and after steps run once to clean up.

A step marked Capture passes its result to the following steps of the same iteration, such as an inserted id used by a later select. State captured by before steps is shared with every virtual user.

Transient errors, such as serialization conflicts or connection pool timeouts, are retried with backoff and the user keeps going. Non-transient errors end the user, which then shows as FAILED on the Workers page.
